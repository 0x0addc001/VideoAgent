1. 目的

本文档定义 VideoAgent 的测试策略、测试分层、TDD 工作方式、环境要求、测试用例、质量门禁、缺陷等级和验收标准。

测试不只用于验证完成后的代码，而是软件设计与实现的一部分。每项业务能力都应先通过失败测试明确行为，再实现代码使其通过，最后在不改变外部行为的前提下重构。

2. 测试原则

2.1 TDD 循环

所有核心业务能力遵循 Red–Green–Refactor：

  1. Red： 根据验收场景编写一个最小失败测试。
  2. Green： 编写足以通过测试的最简单实现。
  3. Refactor： 消除重复、改善命名和结构，保持测试通过。
  4. Commit： 测试和实现可以在绿色状态后一起提交。

禁止先完成大段实现，再事后补写只验证当前实现的测试。

2.2 测试行为而非实现

  • 测试公开行为、业务规则和接口契约。
  • 避免直接断言私有函数、内部调用顺序或数据库实现细节。
  • 外部 Provider 通过接口边界 Mock，不 Mock 被测系统自身的领域逻辑。
  • 时间、随机数和 UUID 使用可注入 Clock 或 ID Provider，保证测试确定性。

2.3 测试金字塔

             E2E
         少量关键流程
        ─────────────────
          Contract / API
        前后端契约与接口
      ─────────────────────
        Integration Tests
      真实 DB / Queue / S3
    ─────────────────────────
           Unit Tests
      快速、大量、无外部依赖

建议比例：

  • 单元测试：60%–70%。
  • API、契约和集成测试：20%–30%。
  • E2E 和人工探索测试：5%–10%。

比例是参考值，不应为了达到数量而编写低价值测试。

3. 质量目标

3.1 自动化覆盖目标

范围 目标
领域规则和权限逻辑 分支覆盖率不低于 90%
LangGraph 节点和状态迁移 分支覆盖率不低于 90%
Provider 参数标准化 分支覆盖率不低于 90%
FastAPI 后端整体 行覆盖率不低于 80%
前端核心业务组件 行覆盖率不低于 80%
Pippit CLI Adapter 契约测试覆盖状态、积分、提交和查询
中英文界面 所有 MVP 页面均有 E2E 场景

覆盖率只是质量指标之一。以下任一情况不能被高覆盖率抵消：

  • 存在未处理的 P0/P1 缺陷。
  • 计费任务存在重复提交风险。
  • 用户能够访问其他用户的数据。
  • Token 会出现在浏览器或日志中。
  • 中英文任一语言存在阻断流程的缺失文案。

3.2 稳定性目标

  • CI 测试连续运行三次结果一致。
  • 非外部依赖测试的 Flaky Rate 低于 1%。
  • 同一失败测试重跑通过不能作为长期修复。
  • 所有 Flaky 测试必须建立跟踪记录，并在发布前修复或隔离。

4. 测试范围

4.1 纳入范围

  • 用户注册、登录、退出和会话。
  • 用户语言偏好。
  • 项目创建、读取、修改、归档和删除。
  • 项目数据所有权隔离。
  • 图片和视频上传。
  • Agent 对话、结构化输出和工作流状态。
  • 中文和英文 Agent 输出。
  • Pippit CLI 服务端授权状态和积分读取。
  • Pippit CLI 命令参数、JSON 输出和任务状态映射。
  • 生成任务提交、轮询、取消、失败和恢复。
  • 任务幂等和重复扣费防护。
  • Celery 消息重复、丢失和 Worker 重启。
  • SSE 状态推送和断线重连。
  • FFmpeg 合成、缩略图和 MP4 导出。
  • 公开分享链接、有效期和撤销。
  • API 契约、输入校验、权限和错误码。
  • 安全、性能、可访问性和可观测性。

4.2 暂不纳入

  • 未实现的支付和计费系统。
  • 多用户实时协作。
  • 数字人、音乐和声音克隆。
  • 原生移动 App。
  • 第三方服务内部推理质量。
  • Pippit 模型输出的艺术质量自动评分。

视频艺术质量采用人工验收，自动化测试只验证任务、媒体格式和业务状态。

5. 测试分层

5.1 单元测试

后端使用 pytest，前端使用 Vitest。

重点对象：

  • Pydantic Schema 和字段约束。
  • 项目、镜头和任务状态机。
  • Agent 节点输入输出。
  • Provider 请求和响应映射。
  • 权限判断。
  • 幂等键生成和费用预算判断。
  • 分享 Token 生成与验证。
  • FFmpeg 参数构造。
  • 中英文翻译键选择。

单元测试不得访问网络、PostgreSQL、Redis、MinIO、Pippit 或真实 LLM。

5.2 Provider 契约测试

为 VideoProvider 定义共享契约测试，所有实现都必须通过：

  • MockVideoProvider
  • PippitVideoProvider

至少验证：

  • 支持能力与声明的 Capability 一致。
  • 无效参数在调用 Provider 前被拒绝。
  • Provider 错误被转换为标准错误码。
  • 任务提交返回稳定的 Provider Job ID。
  • 状态查询返回标准状态。
  • 取消能力不支持时返回明确错误。
  • 原始响应可以保存，但不直接进入领域模型。

5.3 API 测试

使用 FastAPI TestClient 或 ASGI Transport：

  • HTTP 状态码。
  • 响应 Schema。
  • 错误响应格式。
  • 认证和所有权。
  • 分页和排序。
  • Idempotency-Key。
  • CSRF 和 Origin 校验。
  • OpenAPI 契约是否与生成客户端一致。

5.4 集成测试

使用真实 PostgreSQL、Redis、MinIO 和 Celery Worker：

  • 数据库约束和事务。
  • LangGraph Checkpoint 恢复。
  • Alembic 从空数据库升级。
  • Celery 任务投递和执行。
  • Redis Pub/Sub 到 SSE。
  • S3 预签名和对象生命周期。
  • Pippit CLI 使用本地 Fake CLI 可执行文件或受控网络 Stub。

集成测试使用 Testcontainers 或 Docker Compose，每个测试套件使用独立数据库和 Bucket。

5.5 E2E 测试

使用 Playwright 覆盖：

  • 中文和英文完整用户流程。
  • 登录或测试会话注入。
  • 创建项目。
  • Agent 生成故事板。
  • 审批生成。
  • Mock Provider 生成任务。
  • SSE 状态更新。
  • 镜头编辑和重排。
  • 视频导出。
  • 公开分享页。
  • 错误、空状态和恢复。

5.6 非功能测试

包括：

  • 安全。
  • 性能。
  • 可靠性。
  • 可访问性。
  • 可观测性。
  • 浏览器兼容性。

6. TDD 开发流程

6.1 单个功能流程

确认验收场景
  → 编写场景编号
  → 写最小失败测试
  → 运行确认因预期原因失败
  → 实现最小代码
  → 测试通过
  → 重构
  → 运行受影响测试
  → 提交

“测试失败”必须是因为缺少目标行为，而不是导入路径、测试环境或语法错误。

6.2 测试先行顺序

每个功能按以下顺序编写测试：

  1. 领域失败用例。
  2. 领域成功用例。
  3. 权限和边界条件。
  4. API/Provider 契约。
  5. 集成行为。
  6. 前端交互。
  7. E2E 验收。

6.3 Definition of Done

一个任务只有满足以下条件才完成：

  • 验收场景有自动化测试或明确的人工测试步骤。
  • 新逻辑有单元测试。
  • API 或 Provider 变化有契约测试。
  • 跨组件流程有必要的集成或 E2E 测试。
  • 中文和英文文案同时完成。
  • Ruff、mypy、pytest、前端类型检查和测试通过。
  • 没有新增 P0/P1 缺陷。
  • 安全日志不包含敏感信息。
  • 相关文档同步更新。

7.1 本地测试

PostgreSQL
Redis
MinIO
Mock Pippit CLI
Mock Video Provider
Mock LLM Provider

Pippit CLI 的 stdout JSON 契约通过本地 Fake CLI 模拟。真实 Pippit 网络测试默认关闭。

7.2 CI 测试

普通 Pull Request 只运行：

  • 后端单元测试、API 测试和契约测试。
  • 前端单元测试、类型检查和构建。
  • OpenAPI 与生成客户端一致性检查。
  • 静态安全和依赖扫描。

Nightly 任务运行：

  • PostgreSQL、Redis、MinIO 和 Celery 集成测试。
  • Playwright E2E。
  • 迁移与恢复测试。

受保护的 Release 流程运行：

  • Pippit CLI 状态和积分只读 Smoke Test。
  • 经人工授权的一次付费生成测试。

7.3 真实 Pippit 测试开关

真实测试必须同时满足：

RUN_PIPPIT_LIVE_TESTS=1
RUN_PIPPIT_PAID_TESTS=1
PIPPIT_PAID_TEST_BUDGET>0

付费测试还需要：

  • 使用专用测试账户。
  • 指定单次生成次数上限。
  • 指定最大积分预算。
  • 人工启动。
  • 测试后核对任务和积分流水。
  • 默认 CI 中强制关闭。

8. 测试数据

  • 只使用合成用户、合成图片和公开授权测试素材。
  • 不在 Fixture 中保存真实 Pippit Access Key 或 CLI 登录文件。
  • 不在测试日志中输出 Access Key 或完整 CLI 环境变量。
  • 测试用户邮箱使用无投递需求的合成地址，例如 creator@example.com。
  • 每个测试使用独立 UUID 和数据库事务。
  • 测试结束后删除数据库记录、对象存储文件和临时媒体。
  • 数据库测试禁止连接共享生产数据库。

10. 状态与恢复专项测试

10.1 LangGraph 恢复

测试以下状态保存与恢复：

awaiting_plan_approval
awaiting_generation_approval
submit_generation_jobs
wait_for_jobs
review_results
await_export_approval

每个状态至少验证：

  • 进程重启后状态不变。
  • 重复提交审批不会创建重复任务。
  • 未审批状态无法跳过。
  • 已完成状态不会被重复执行。

10.2 Celery 故障

使用受控故障注入：

  • Worker 在收到任务前退出。
  • Worker 在调用 Pippit 前退出。
  • Worker 获得 Provider Task ID 后退出。
  • Worker 下载媒体失败。
  • Redis 短暂不可用。
  • 同一任务被重复投递。

预期系统最终进入一致状态，不重复扣费，不丢失已成功的 Provider 任务。

10.3 SSE 故障

  • 浏览器断网后重连。
  • FastAPI 重启。
  • Redis Pub/Sub 消息暂时丢失。
  • 多个 API 实例订阅同一项目。
  • 客户端收到重复事件。

客户端必须根据完整 REST 状态去重和校正。

11. 性能测试

MVP 基线：

  • 普通 API 不含 Provider 调用时，P95 小于 300 ms。
  • 项目列表和故事板接口在 100 个镜头内保持可接受响应。
  • SSE 心跳间隔 15–30 秒。
  • 单 Worker 可并发处理配置数量的查询任务。
  • 同一任务的并发提交只能成功一次。
  • 100 个前端事件连续到达时，界面不出现明显卡顿。

性能测试不把 Pippit 推理时间计算为 API 响应时间。Provider 排队和生成时间单独统计。

13. CI 质量门禁

13.1 Pull Request 门禁

以下任一失败阻止合并：

  • Ruff 检查或格式化失败。
  • mypy 类型检查失败。
  • 后端单元、API、契约测试失败。
  • 前端类型检查、Lint 或组件测试失败。
  • OpenAPI 与生成客户端不一致。
  • 数据库迁移测试失败。
  • 新增高危依赖漏洞。
  • 命中敏感信息扫描。

13.2 Nightly 门禁

  • PostgreSQL、Redis、MinIO 集成测试。
  • Celery Worker 测试。
  • Playwright 中文和英文 E2E。
  • 数据库迁移从空库升级。
  • 故障恢复测试。
  • 浏览器兼容性测试。

13.3 Release 门禁

  • 所有自动化测试通过。
  • 无 P0/P1 未解决缺陷。
  • Pippit 状态和积分只读 Smoke Test 通过。
  • 生产配置和 Secrets 检查通过。
  • 数据库备份与回滚步骤确认。
  • 经授权完成付费生成验收，或有明确风险接受记录。

14. Pippit 真实测试流程

14.1 只读 Smoke Test

人工触发，不消耗积分：

  1. 在 API 主机安装 @pippit-dev/cli@1.0.48 或更新版本。
  2. 使用受控测试账户执行 pippit-tool-cli login。
  3. 执行 pippit-tool-cli status。
  4. 执行 pippit-tool-cli get-credit-balance。
  5. 调用 /providers/pippit 和 /providers/pippit/credits。
  6. 验证日志不包含 Access Key 或 CLI 登录状态内容。

14.2 付费生成测试

仅限发布前人工执行：

  1. 记录起始积分。
  2. 用户明确批准预算。
  3. 创建 1 个最小视频生成任务。
  4. 验证 Provider Task ID 只保存一次。
  5. 轮询至完成。
  6. 下载并校验媒体。
  7. 记录任务和积分变化。
  8. 验证重复请求不会再次提交。
  9. 执行 FFmpeg 合成或单镜头导出。
  10. 审核 UI、事件和数据库状态一致性。

测试报告必须记录测试时的实时 Pippit 余额，不得在代码或文档中硬编码账户数值。 余额为 0 时跳过付费测试，不自动充值。

16. 缺陷等级

等级 定义 处理要求
P0 数据泄露、跨用户访问、重复扣费、无法登录、无法生成 立即停止发布
P1 核心流程受阻、任务无法恢复、中英文关键页面不可用 发布前必须修复
P2 非关键功能异常、明显体验问题或有限范围错误 评估修复或记录
P3 轻微视觉、文案或低概率问题 可进入后续迭代

17. TDD 实施顺序

第 1 轮：测试基础设施

  1. 配置 pytest、Vitest、Playwright。
  2. 创建测试标记和目录。
  3. 实现 Fake Clock、UUID、LLM、Pippit CLI、Provider 和 Storage。
  4. 建立测试数据库和迁移测试。
  5. 配置 CI 报告。

第 2 轮：健康检查

  • 先写 /health 失败测试。
  • 实现最小 FastAPI 应用。
  • 增加数据库和 Redis 健康状态。

第 3 轮：认证与权限

  • 测试先行实现注册、登录、会话。
  • 测试先行实现项目所有权。
  • 测试先行实现 CSRF 和访问控制。

第 4 轮：国际化

  • 测试先行实现 /en 和 /zh-CN。
  • 测试语言切换和偏好保存。
  • 建立翻译键完整性检查。

第 5 轮：项目与故事板

  • 测试先行定义 Project、Shot 和状态迁移。
  • 实现版本控制和并发更新。
  • 实现故事板 API。

第 6 轮：资产与存储

  • 测试先行实现预签名和文件校验。
  • 实现素材元数据和缩略图。
  • 测试跨用户隔离。

第 7 轮：Agent

  • 测试先行定义 Pydantic 输出。
  • 实现单节点 Agent。
  • 逐步加入创意、故事板、审批和审核节点。
  • 使用 Fake LLM 保证确定性。

第 8 轮：Provider 与 Pippit

  • 先定义 Provider 共享契约。
  • 先实现 Mock Provider。
  • 再实现 Pippit CLI Adapter。
  • 测试状态、余额、提交和查询 JSON 映射。
  • 测试 CLI 缺失、超时、非零退出码和无效 JSON。

第 9 轮：任务执行

  • 测试幂等键和任务状态。
  • 实现 Celery 提交和轮询。
  • 注入 Worker 重启和重复投递。
  • 实现 SSE 和恢复。

第 10 轮：媒体与分享

  • 测试 FFmpeg 参数构造和失败处理。
  • 实现合成、导出和缩略图。
  • 测试分享 Token、过期和撤销。

第 11 轮：E2E 与发布

  • 使用 Mock Provider 完成中英文全流程。
  • 执行 Pippit 状态和积分只读测试。
  • 在用户批准预算后执行一次付费测试。

19. 风险和约束

风险 测试措施
LLM 输出不确定 Fake LLM、结构化 Schema、固定 Fixture、重试测试
Pippit 真实接口不可控 Fake CLI Contract、受控只读 Smoke Test、CLI 版本记录
付费测试成本 默认关闭、人工开关、单次预算、积分核对
长任务测试缓慢 可注入轮询间隔和 Fake Clock
媒体文件体积大 使用小样本 Fixture、测试后清理
E2E 容易 Flaky 稳定测试选择器、事件驱动等待、禁止固定长 Sleep
中英文内容不同步 翻译键检查、双语言 E2E
并发任务重复 Idempotency-Key、数据库锁、重复投递测试

20. 完成标准

测试体系达到以下条件后，视为具备稳定 TDD 开发基础：

  1. 本地一条命令启动测试依赖。
  2. 后端单元和 API 测试可在无网络环境运行。
  3. Mock Provider 可完成项目、故事板、生成和导出全流程。
  4. 集成测试可验证 PostgreSQL、Redis、MinIO 和 Celery。
  5. 中文和英文关键 E2E 用例稳定通过。
  6. CI 阻止失败测试、类型错误和契约不一致进入主分支。
  7. 真实付费生成默认不在 CI 中运行。
  8. 所有 P0 场景均有用例。
  9. 每次发布生成可追溯的测试报告。
  10. 新增功能遵循 Red–Green–Refactor，而不是实现后补测试。
