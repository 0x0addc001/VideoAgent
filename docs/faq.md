## Q1. VideoAgent 的主编排应怎样设计？

**答案**

VideoAgent 采用确定性工作流：Brief（创作需求简报）、创作诊断、
Treatment（创作阐述）、Script/Beats（剧本与叙事节拍）、
Storyboard（故事板）、连续性校验、预演、生成、镜头 QC（质量检查）、粗剪和交付。故事方向、预算和
成片方向设置人工确认点，模型负责创意，代码负责状态、权限和成本边界。

**追问：** 为什么不直接使用多个自由 Agent？

**答案**

职责共享同一上下文时，单 Agent 配明确工具和状态更稳定。只有剧本、视觉、
制片和审片具有真正独立的工具、上下文和验收标准时，才拆成受限子 Agent，
由父流程协调。

**扩展：** LangGraph（图式工作流编排框架）

**答案**

使用 StateGraph（状态图）表达阶段和条件边，checkpoint（可恢复的流程快照）
保存状态，human-in-the-loop（人工介入确认）负责关键确认，
tool allowlist（工具白名单）限制能力边界，结构化输出
保证节点间契约稳定。

## Q2. 用户说“只改第三镜，其他不要动”，系统应如何实现？

**答案**

先识别意图，再把修改落到稳定的 shot id（镜头唯一标识）上。
Agent 输出局部 shot patch（单镜头局部修改补丁），
记录版本和操作日志，其他镜头及其审批状态保持不变。

**追问：** 如果用户只是问“这个分镜怎么样”，也应该重写故事板吗？

**答案**

不应该。只评估请求进入 review（评估）分支，返回问题和建议，不产生写操作。

**扩展：** 局部修改如何保证并发安全？

**答案**

使用乐观锁（更新时检查版本是否仍一致）或版本条件更新；同一请求携带
幂等键（同一请求重复提交也只执行一次）；镜头修改与后续生成任务通过
依赖关系关联，避免旧版本结果覆盖新镜头。

## Q3. 一个可生成的专业镜头，至少需要哪些字段？

**答案**

除 Prompt、时长和画幅外，还需要 scene/beat（场景与叙事节拍）、叙事功能、景别、机位、镜头、
运镜、主体动作、视线、走位、光线、色彩、声音、转场、连续性引用和前后景状态。

**追问：** 为什么 Prompt 写得足够长仍然不够？

**答案**

Prompt 是单次生成描述，不承担结构化约束。人物、空间、视线和服装的一致性需要
独立字段、引用资产和跨镜头校验。

**扩展：** 需要哪些电影语法？

**答案**

使用 master/medium/close/insert/reaction（全景/中景/近景/插入/反应镜头）
组织覆盖，检查 180 度规则、30 度规则、eyeline match（视线匹配）、
screen direction（屏幕方向）、match cut（匹配剪辑）和有动机的运镜。

## Q4. 如何让 LLM 输出真正可执行？

**答案**

用 Pydantic（Python 数据校验库）定义严格输出结构，校验字段、时长、比例、
镜头数量和引用关系。执行前再做 Provider（模型服务商）能力匹配，确认模型支持目标时长、音频和输入类型。

**追问：** 模型返回 JSON（结构化数据格式）后还需要做什么？

**答案**

JSON 只是候选结果。系统要继续做 Schema（字段结构定义）校验、业务校验、权限检查和费用检查，
全部通过后才进入写库或生成阶段。

**扩展：** 校验失败怎么处理？

**答案**

允许有限次结构化修复；修复预算耗尽后返回稳定错误码，不进入计费链路，也不把
异常文本直接交给下一个工具。

## Q5. MCP（模型上下文协议）和 CLI（命令行接口）应该怎么选？

**答案**

按运行边界选择。服务端批处理和稳定部署使用 CLI；跨 Agent、个人 Agent 和
工具发现场景使用 MCP。两种协议都收敛到统一 Provider（模型服务商）契约。

**追问：** 两者同时存在会不会重复建设？

**答案**

不会。重复的是底层能力，不重复的应是接口。传输层分别适配 CLI 和 MCP，
业务层只依赖 estimate（估算）、submit（提交）、status（查询）、
cancel（取消）和统一错误模型。

**扩展：** Provider 适配器要标准化什么？

**答案**

标准化模型能力、任务引用、状态、错误码、结果 URL、积分和取消语义；凭据只在
适配器内部使用，不进入浏览器或领域对象。

## Q6. 生成任务超时后怎么办？

**答案**

计费提交超时先进入 `submission_uncertain`（提交结果不确定）状态，保留
幂等键（同一请求重复提交也只执行一次）和请求记录，再查询
Provider（模型服务商）对账。无法确认是否受理时停止自动重试并告警。

**追问：** 可以自动重试三次吗？

**答案**

普通只读查询可以退避重试；计费提交不能盲目重试。只有确认未受理或通过幂等键
找到同一任务后，才能继续。

**扩展：** 怎样防止重复扣费？

**答案**

数据库唯一幂等键、提交状态机（状态及合法迁移规则）、
Provider Task Reference（服务商任务编号）和人工可解释的对账流程
共同保证 at-least-once（至少一次投递）不会变成重复计费。

## Q7. VideoAgent 的评测应该怎么做？

**答案**

按阶段评测。剧本看欲望、冲突、转折和结尾；故事板看覆盖、连续性和可生成性；
镜头看人物、Prompt 匹配和技术瑕疵；成片看节奏、声音和观看留存。

**追问：** 故事板阶段需要视觉质量分数吗？

**答案**

不需要。故事板阶段不显示制作进度条；人物一致性、风格一致性等视觉指标应面向
Final Cut，由用户选择已配置的视觉评估模型，
基于成片帧和明确 rubric 计算；评估器不可用时不得生成伪造分数。

**扩展：** 怎样降低 Judge 偏差？

**答案**

固定 rubric、盲化模型来源、pairwise 比较、多人标注校准，并持续监控
inter-rater agreement 和 gaming resistance。

## Q8. 如何保证多镜头的人物与场景一致性？

**答案**

建立 Style Bible（视觉风格手册），分别管理角色、服装、场景、道具和视觉基调；每个镜头引用
对应资产，生成前检查视线、屏幕方向和空间关系。

**追问：** 只把同一段描述放进每个 Prompt 够吗？

**答案**

不够。文本描述无法稳定锁定身份和空间，必须使用结构化引用、首尾帧或
subject reference，并在生成后做一致性检查。

**扩展：** 发现不一致时重做全部镜头吗？

**答案**

只重做受影响的镜头。通过 continuity graph（连续性依赖图）找到依赖节点，
保留已通过的镜头。

## Q9. 如何控制积分成本和用户预期？

**答案**

按序列或制作包展示预算，区分预览、正式镜头和备选 take（镜头候选版本）。
高成本生成前先完成低成本 Animatic（动态分镜预演），重做时说明原因和预计费用。

**追问：** 每个镜头都弹确认框是不是就够了？

**答案**

不够。逐镜确认只能防单次误操作，不能控制整段视频预算。需要序列预算、
额度预留和超预算停止机制。

**扩展：** 成本系统要记录什么？

**答案**

记录估算、批准人、幂等键（同一请求重复提交也只执行一次）、
Provider（模型服务商）成本、实际积分、重试原因和最终 take（镜头候选版本），
形成可核对的 credit ledger（积分流水）。

## Q10. 如果线上生成成功率突然下降，如何定位问题？

**答案**

先按状态机定位失败发生在提交前、提交不确定、排队、运行、下载还是完成阶段，
再按 Provider（模型服务商）、模型、地区和发布时间切分。

**追问：** 应最先看模型质量还是基础设施？

**答案**

先看可观测信号判断故障边界，不先归因模型。错误码、超时、队列和下载指标能
快速区分基础设施、Provider 与内容策略问题。

**扩展：** 怎样设计观测体系？

**答案**

用 trace（调用链追踪）串起 project（项目）、shot（镜头）、job（任务）和
provider task（服务商任务），记录结构化日志、SLI/SLO（服务质量指标与目标）、
延迟、成功率、幂等拦截和积分消耗，并配置 canary（灰度发布）、
feature flag（功能开关）和 kill switch（紧急停用开关）。

## Q11. 为什么不用一个无限自主的 Agent 完成所有事情？

**答案**

视频创作同时包含创意不确定性和不可逆成本。无限自主会让权限、预算、状态恢复
和审计难以证明，应采用“高自主创意、强约束生产”。

**追问：** 自主性越高不是越智能吗？

**答案**

自主性提高的是可行动空间，不等于决策质量。生产 Agent 需要边界、确认门和
可回放状态，才能把能力转化为稳定交付。

**扩展：** 哪些动作必须人工确认？

**答案**

计费生成、批量重做、删除资产、公开发布、修改权限和改变预算必须走白名单工具
与人工确认。

## Q12. VideoAgent 最关键的工程原则是什么？

**答案**

把创意决策表示为可校验、可追踪、可局部修改的结构化数据，让 Agent 的推理结果
能够进入可靠的生产状态机。

**追问：** 为什么这个原则比增加更多 Agent 更重要？

**答案**

没有稳定数据契约，更多 Agent 只会放大上下文漂移和状态不一致。结构化数据让
分工、恢复、评估和局部重做成为可验证行为。

**扩展：** 最重要的基础字段是什么？

**答案**

scene、beat、story function、镜头语言、主体动作、连续性引用和生成能力要求。
这些字段共同连接预演、生成、评估与剪辑。

## Q13. VideoAgent 的主要技术权衡是什么？

**答案**

核心权衡包括延迟、质量和成本，自主性与可控性，一致性与创作灵活性，
单 Agent 与多 Agent，轮询与实时推送。架构选择应服务于当前瓶颈，而不是追求
概念上的“更智能”或“更分布式”。

**追问：** 什么时候应从单 Agent 拆成多 Agent？

**答案**

当子任务具有独立工具、上下文、评估标准和扩缩容需求时再拆分。仅靠增加 Agent 无法解决上下文漂移，反而会增加协调、追踪和一致性成本。

**扩展：** 如何避免架构过度设计？

**答案**

先量化瓶颈来自创意质量、Provider（模型服务商）延迟、队列积压还是数据库竞争，再选择最小
改动。每次扩展都要求可观测指标证明收益大于运维复杂度。

## Q14. 视频生成系统如何支撑高并发？

**答案**

API（应用程序接口）只负责鉴权、校验和入队，不在请求线程中等待生成；
Worker（后台任务进程）按 Provider（模型服务商）配额消费任务。通过用户、
IP（网络地址）、租户和 Provider
分层限流，配合有界队列（容量限定的任务队列）、并发信号量（限制同时运行任务数）、
幂等键（同一请求重复提交也只执行一次）、连接池和背压（下游过载时向上游减速）控制吞吐。

**追问：** Provider 并发额度耗尽时怎么办？

**答案**

任务进入公平队列，按租户、优先级和截止时间调度；向客户端返回可解释的排队
状态。计费提交禁止因限流盲目重试，扩缩容也不能突破 Provider 的硬配额。

**扩展：** 如何实现优雅过载？

**答案**

使用有界队列、load shedding（主动丢弃超载请求）、circuit breaker（熔断）
和降级预览；优先保护已受理任务，
明确拒绝超出容量的新请求，并暴露队列深度、等待时间和拒绝率。

## Q15. VideoAgent 如何设计高可用？

**答案**

API（应用程序接口）保持无状态并多实例部署，数据库保存业务事实，
Redis（内存数据结构存储）只承担缓存、队列和
协调。服务提供健康检查、滚动发布、超时和熔断；Provider 通过统一适配器支持
受控切换。

**追问：** 数据库或 Redis 故障时如何降级？

**答案**

数据库故障时停止新增写操作，优先维持只读；Redis 故障时保护数据库，暂停队列
消费并从持久化任务恢复。幂等键和对账记录必须保留，避免恢复后重复提交。

**扩展：** 高可用验收应包含什么？

**答案**

先定义 RTO/RPO（恢复时间目标/恢复点目标），再演练实例故障、数据库切换、队列恢复、Provider（模型服务商）故障和区域
故障；没有恢复演练的高可用架构不能视为完成。

## Q16. 视频生成链路应怎样设计兜底策略？

**答案**

兜底分四层：显式模型降级、Provider（模型服务商）切换、
低成本预览或 Animatic（动态分镜预演）、只读缓存与
错误说明。任何降级都要说明质量、价格和能力差异，不能静默替换模型或产生额外
费用。

**追问：** Provider 超时后能否直接切换另一家重做？

**答案**

先通过幂等键和任务引用确认是否已受理。无法确认时停止计费重试；确认未受理且
用户策略允许后，才可切换到备用 Provider。

**扩展：** 兜底策略的优先级如何确定？

**答案**

依次考虑数据安全、费用一致性、结果可用性、质量和延迟。降级必须可观测、可
解释、可撤销，并受用户预算和内容策略约束。

## Q17. VideoAgent 的 Loop 是什么？

**答案**

当前是受控的单次规划 Run，不是无限自主的 ReAct 循环。FastAPI 接收用户消息后，
依次保存 `run_id`、构建有界 Context、读取 Memory 和当前项目资源、解析可选 Skill，
再执行 LangGraph 的单个 `plan_storyboard` 节点。Planner 输出
`StoryboardPlan`，经 Pydantic 校验后写入工作流、Message、Character 和 Shot 状态，
最后生成导演回复。

**追问：** 为什么还能在等待界面看到很多步骤？

**答案**

每一步都会写入 `agent_activities`，前端按 `run_id` 轮询并显示
`context → memory → skill → planning → validation → state → reply` 的真实事件。
它不是用假动画模拟工具执行；没有发生的 MCP 或 Skill 调用不会显示为已完成。

**扩展：** 什么时候才需要真正的多轮 Loop？

**答案**

当 Agent 需要根据工具结果决定下一步，例如自动读取素材、调用视觉评估、根据失败原因
重试或请求用户补充信息时，才需要把单节点图扩展为有预算、有终止条件、有审批门和
可恢复 Checkpoint 的多节点循环。

## Q18. VideoAgent 的 Context 和 Memory 怎么设计和管理？

**答案**

Context 是单次规划调用的有界输入，包含项目标题、Brief、当前请求、Locale、
工作流阶段/状态、当前 Character/Shot 摘要、最近对话和可选 Skill 指令。短期 Memory
只读取最近 8 条历史消息，每条截断到 600 字符，并排除当前请求；故事板上下文最多
读取 20 个 Shot。

**追问：** 长期 Memory 存在哪里？

**答案**

关系数据库是唯一事实来源，保存 Project、Conversation、Message、
ProjectWorkflow、Storyboard、Character、Shot、Asset 和 GenerationJob。当前没有
向量数据库、跨项目用户记忆或自动长期摘要。

**扩展：** 以后增加向量 Memory 要注意什么？

**答案**

必须有用户和项目级隔离、写入去重、TTL、删除传播、权限校验和可解释召回；召回内容
只能作为有界 Context 的一部分，不能取代数据库状态或审批记录。

## Q19. VideoAgent 的 Skill、MCP、SubAgent 是怎么调用的？

**答案**

Skill 当前不是工具执行。Composer 把 Skill ID 写入项目 `Production settings`；
Context Builder 会在当前用户已发布的 Skill 中查找它，并把持久化的 instructions
和 starter prompt 加入 Planner Context。内置 Skill 没有数据库指令时，只传入
Skill ID 作为创作约束。

**追问：** Storyboard Agent 会直接调用 MCP 吗？

**答案**

不会。MCP 位于付费生成 Provider 边界之后。用户明确批准生成后，Generation API
才解析 Provider；当 Kling 使用 MCP Backend 时，Provider Resolver 使用当前用户的
OAuth Token 创建 `StreamableHTTPToolClient`，再由 `KlingVideoProvider` 调用
`text_to_video`、`image_to_video` 或 `query_tasks`。默认国内版路径使用受控 CLI
子进程。这样可以阻止规划 Agent 自行产生计费副作用。

**扩展：** 现在有 SubAgent 吗？

**答案**

没有。当前只有 LangGraph 的单个 `plan_storyboard` 节点，没有独立 SubAgent
运行时、委派协议或并行子图。只有在剧本、视觉、评估或制片任务具备独立工具、
上下文、验收标准和扩缩容需求时才应拆分；拆分后每个 SubAgent 仍需共享可追踪
`run_id`、预算和审批边界。

## Q20. VideoAgent 中的 Hook 是什么，目前怎么用？

**答案**

Agent Hook 是 Agent 执行生命周期上的拦截点，用于在指定阶段注入 Context、执行策略
校验、记录审计、阻断不安全操作或触发外部自动化。

当前 VideoAgent 在 Agent Run 内提供可观测的阶段 Hook：`context`、`memory`、
`skill`、`planning`、`validation`、`state` 和 `reply`。这些事件由
`AgentActivityRecorder` 按 `run_id` 持久化，前端用它们展示真实的执行轨迹。模型调用
本身仍是单个 LangGraph `plan_storyboard` 节点；生成工具位于审批边界之后，不会由
规划 Agent 直接触发。

**追问：** Agent Hook 和 Skill、MCP 有什么区别？

**答案**

Skill 定义 Agent 要完成什么任务以及执行规范；MCP 连接可调用的外部工具和数据源；
Agent Hook 则挂在执行阶段边界上，决定某一步前后需要额外执行什么治理逻辑。Hook
不会替代 Skill 的创作指令，也不会直接变成一个生成工具。

**扩展：** 为什么不能把所有步骤都做成无限 Hook？

**答案**

Hook 越多，延迟、循环调用、状态一致性和故障传播越难控制。每个 Hook 都应有明确的
触发阶段、超时、幂等语义、错误策略和审计记录；计费工具仍必须经过显式审批，不能借
Hook 绕过预算和 Provider 边界。

## Q21. VideoAgent 如何在同一个 Skill 有多个 Provider 时选择模型？

**答案**

Agent 按任务与能力整理候选：文生文、文生图、图生图、文生视频或图生视频；图片、
视频、主体、关键帧和音频引用；时长、画幅、语言、声音、输出质量、Provider 可用性与
预计积分。项目默认模型会被预选，但不会永久锁死。如果两个 Provider 都能完成同一
Skill，任务页会展示可选的 `服务商/模型`，用户通过估算或生成进行确认，系统不会静默
切换服务商。

**追问：** 项目开始后还能更换模型吗？

**答案**

可以。Character 和 Scene 提供图片模型选择，Shot 提供视频模型选择，文生视频和图生视频
都使用当前选择。“Project default”继承初始设置；显式切换只影响下一次生成，并使旧积分
估算失效。计费任务一旦被 Provider 接受，不会在用户不知情时切换 Provider。

**扩展：** 文生文规划模型也能切换吗？

**答案**

规划模型也遵循相同的任务路由原则，但当前部署只开放管理员配置的 Planner。若以后配置
多个规划模型，应在 Settings 中展示推理能力、Context、延迟和价格差异。一个模型生成的
内容不能描述成另一个模型的产出。

## Q22. VideoAgent 现在支持哪些多模态制作能力？

**答案**

VideoAgent 支持有顺序的图片、视频和音频参考；Character 与 Scene 的文生图和图生图；
Shot 的文生视频和图生视频；Kling 4.0 最长 30 秒，以及 21:9、16:9、9:16、1:1 输出。
已安装的 Kling 4.0 CLI 声明 10 个图片槽、5 个视频槽和 3 个音频槽，合计最多 15 个
参考素材。Agent 只提交所选模型实际支持的参考组合。

**追问：** 关键帧如何排序？

**答案**

参考素材按 Shot Prompt 中 `@asset-id` 的出现顺序传递，界面与 Provider 边界都会保留
该顺序。关键帧槽位映射取决于模型：支持关键帧的图生视频模型接收首帧、中间帧和尾帧，
全能参考模型则接收有顺序的图片、视频和音频输入。

## Q23. Celery 和 Redis 在 VideoAgent 中如何配合？

**答案**

生成接口先在关系数据库创建或恢复 `GenerationJob`、预扣积分并调用 Provider 提交任务，
提交成功后提交数据库事务。随后 API 通过 `poll_generation_job.delay(job_id)` 把任务
放入 Celery；Celery 使用 Redis DB 0 作为 Broker 传递任务，使用 Redis DB 1 作为 Result
Backend。Worker 消费任务后创建独立数据库 Session，调用 `refresh_generation_job`
查询一次 Provider；未结束时通过 `self.retry` 延迟重试，间隔按
`5 × 2^retries` 增长并封顶 120 秒，直到任务成功、失败或取消。

Redis 只承担“任务传递”和“执行结果回传”，`GenerationJob`、Shot 状态、积分流水和
素材归属仍以关系数据库为唯一事实来源。Celery 配置了延迟确认、Worker 丢失后重新投递、
单任务预取和启动连接重试，避免 Worker 异常时任务被提前确认。

**追问：** Redis 或 Celery 暂时不可用时会不会卡死？

**答案**

不会把已提交的生成任务丢掉。API 在提交 Provider 后先持久化 Job，再尝试投递 Celery；
即使 Redis 入队失败，接口仍返回已持久化的 Job，前端可通过 `GET /jobs/{id}` 直接轮询
Provider 状态。Redis 恢复后再根据持久化任务做补偿，而不是相信内存队列是唯一事实源。

**追问：** 为什么不直接在 FastAPI 请求线程里轮询？

**答案**

视频生成可能持续数分钟，占用 Web 请求会耗尽连接和工作线程，也无法在进程重启后继续。
后台 Worker 把长任务与 API 解耦，可以独立扩缩容、限制 Provider 并发并统一重试。

## Q24. VideoAgent 的核心代码在哪里？

**答案**

- `services/api/src/videoagent/api/agent.py`：消息入口、意图路由、Context/Activity
  记录、最终成片就绪检查和响应持久化。
- `services/api/src/videoagent/agent/graph.py`：LangGraph 图定义，当前执行单个
  `plan_storyboard` 节点，并负责活动状态和结构化结果校验。
- `services/api/src/videoagent/agent/planner.py`：本地确定性 Planner、
  OpenAI-compatible/DeepSeek Planner、JSON 兼容回退和远程超时后的本地兜底。
- `services/api/src/videoagent/services/agent_context.py`：项目 Brief、对话、
  Storyboard、Skill 等有界 Context 的组装。
- `services/api/src/videoagent/services/agent_activity.py`：把真实 Agent 执行阶段
  持久化为前端可观测事件。
- `apps/web/src/components/project-workspace.tsx`：Agent 对话、审批、执行轨迹、
  错误弹窗和项目画布交互。

主链路是：接收消息 → 构建 Context → 解析 Skill → LangGraph 规划 → 校验
`StoryboardPlan` → 持久化 Direction/Vision 状态 → 返回可流式展示的回复。远程 Planner
超时或返回不可解析结果时，服务端明确提示本次使用本地 Planner 兜底，不会让请求无限等待。
